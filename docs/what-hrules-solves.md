# Hrules 在实际使用中解决什么

很多代理工具已经能解决“连接代理节点”这一步，但**有节点不等于有正确的分流**。

Hrules 关注的是实际使用过程中更靠后的问题：当一个网站、App 或账户产生多条网络请求时，这些请求最终会进入哪个策略组、使用哪个节点、是否会因为规则遗漏而落入其他出口。

## 1. 让敏感业务使用你指定的出口

AI、银行、支付、证券、虚拟货币等服务往往不是只有一个主域名。一次登录或使用过程可能同时产生主站、认证、API、WebSocket、静态资源、上传以及第三方依赖请求。

Hrules 会把**已经识别并验证归属的请求**组织到对应场景。用户可以为场景选择地区或具体节点，而不是只依赖机场默认规则。

例如：

```text
ChatGPT / OpenAI
        ↓
🤖 AI 服务 [场景]
        ↓
用户选择的地区或节点
```

如果选择具体节点，该场景固定使用这个节点；敏感场景不会为了“保持可用”而静默切换到其他地区、DIRECT 或其他不可预期出口。

## 2. 避免“明明选了节点，部分流量却走了别处”

实际访问一个服务时，请求可能跨多个域名。只给主域名写一条规则，并不能保证整个使用链路都进入同一个场景。

Hrules 的规则维护重点之一，就是通过真实连接记录持续补充和验证这些业务依赖，并把共享基础设施与业务专属域名区分开，避免为了覆盖一个服务而误伤其他网站。

这也是为什么 Hrules 强调**可控、可验证**，而不是简单堆积大量域名。

## 3. 把不同账户场景分开

精细版可以把不同敏感业务拆成独立出口：

```text
🤖 AI 服务
🏦 银行服务
📈 证券 / 券商
💳 支付 / 跨境金融
💰 虚拟货币
```

这些场景可以分别选择节点。例如 AI 使用一个固定出口，银行使用另一个固定出口，虚拟货币使用第三个出口，而不是所有海外流量共享同一个自动选择组。

## 4. 让机场提供节点，而不是决定 Hrules 的规则

使用 Clash Verge Rev 接入 Hrules 后，机场订阅、自建节点等继续提供节点资源；Hrules 接管规则匹配和最终兜底。

也就是说：

```text
机场 / 自建节点
      ↓
提供可用节点

Hrules
      ↓
识别流量 → 场景归类 → 决定交给哪个出口组
```

这样可以避免机场原有规则与 Hrules 同时参与匹配，导致同一业务的流量被两套路由逻辑分别处理。

## 5. 国内直连也要防止误判

Hrules 不采用“只要看起来像中国域名就全部 DIRECT”的简单做法。

中国大陆 DIRECT 数据经过边界保护后再发布，目的是在保持常用国内网站直连的同时，减少宽泛分类把海外服务错误送入 DIRECT 的风险。

## 6. Hrules 不解决什么

Hrules 是**分流规则层**，不是节点或线路优化工具。

它不会：

- 提供代理节点；
- 改变节点的 IP、线路质量、延迟、丢包或协议能力；
- 保证第三方平台账号不触发认证或风控；
- 保证某个地区一定具备服务资格；
- 把质量不佳的节点变成稳定线路。

如果某个请求已经正确命中 Hrules 场景，但实际连接仍然慢或失败，应继续检查最终节点和实际网络路径。

## 7. 怎么确认 Hrules 是否真的在工作？

不要只看“网站能不能打开”，而要看客户端 Connections / 日志：

```text
域名
→ 命中的 Hrules RuleSet
→ 场景策略组
→ 最终节点
→ 实际出口
```

例如看到：

```text
chatgpt.com
→ hrules-sensitive-ai
→ 🤖 AI 服务
→ 你选择的节点
```

才能确认这条请求确实按照预期分流。

对于登录、上传、WebSocket 等复杂场景，还应该观察同一次使用过程中产生的其他请求是否也进入预期场景。
